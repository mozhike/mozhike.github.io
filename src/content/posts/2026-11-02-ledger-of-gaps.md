昨天那篇里写过一条规矩：**已知缺口要登记，未知缺失才叫人。**

今天早上，这条规矩第一次按设计跑完了完整一圈，然后系统在开盘前报出了九个交易日的缺口。

## 一、先看单日巡检为什么会漏

在这次改动之前，晚间的断档检查只看一件事：本地日线库最新的那一天有没有数据。

这个判断在大多数时候是对的，因为它假设“最新的那天在，前面就应该都在”。

但上周发生的事正好相反：周四周五整晚没有运行，周一开机后库才补到周一。巡检看到的是周一——周一有数据，于是结论是“一切正常”。缺掉的那两天，从来没有进入它的视野。

这不是漏报，是视野只有一帧。**只看最新状态的自检，天然看不见“中间断过”。**

## 二、把视野改成五天

改法不复杂：把检查窗口从“最新一天”改成“最近五个交易日”，逐日升序，一天一天单独判断。

每一天的处理分三种：

- 任务支持指定目标日 → 自动补跑；
- 任务不支持指定目标日 → 只标记“需人工”，不自动执行；
- 已经登记为永久缺口 → 只检查存在性，不补、不推送。

第二条是刻意留下的刹车。历史上有过把“今天”的产物写到历史日期的教训，补跑一个不认识目标日的任务，等于主动制造一条假数据。**能补的自动补，不能补的老实标人工，比“全都自动补”安全得多。**

同时，缺口清单从一份说明文档，变成了一份真正参与判断的白名单：登记过的缺口，巡检仍然检查，但不再每次都推送。

## 三、上线首日，报出九天

今早开盘前，按最近二十个交易日回看的日检第一次跑完，推送里列出了九个交易日。

它们不是今天新坏的，而是过去一个月里陆续断掉、但从来没有被系统记账的：

| 日期 | 缺什么 |
|---|---|
| 10月09日 | 市场环境、比对报告 |
| 10月12日 | 预测批次、市场环境、比对报告 |
| 10月13日 | 预测批次 |
| 10月15日 | 预测批次 |
| 10月16日 | 预测批次、市场环境、比对报告 |
| 10月20日 | 市场环境 |
| 10月21日 | 预测批次、市场环境、比对报告 |
| 10月22日 | 预测批次、市场环境、比对报告 |
| 10月23日 | 预测批次、市场环境、比对报告 |

九天里，五天是整晚链路没有跑，四天是跑了但漏了其中一两项。还有两天（10月29日、10月30日）此前已经登记过，这次没有重复报。

在补登记之前，系统对这段历史的认知是“没有未知缺失”。补登记之后，同一个结论变成了“无未知缺失”——字面一样，含义完全不同：前一个是没检查，后一个是检查过、并且知道缺什么。

## 四、为什么先补账本，不补数据

九个交易日，第一反应当然是“能不能补回来”。

答案是分层的，而且大部分补不回来：

**第一类，补不了。** 选股批次需要当天盘中真实跑一遍才能产生。事后用收盘数据反推“那天应该选哪些”，等于用答案编题目——这种数据一旦进样本库，会污染之后所有的统计，比缺一天糟糕得多。

**第二类，能补但不能混。** 有些字段有后备数据源可以还原，比如用历史日 K 反推指数涨跌。但后备源和主口径不是同一套东西，单独落一份留痕可以，写进主表就会让两个口径混在一起比较——那比没有数据更危险。

**第三类，能补但代价大于收益。** 九天历史补完，产出的样本也不会进入当期结论，却要承担一次大面积写库的风险。

所以今天的处置是：把九天全部登记进缺口清单，标记为延后处理，逐条写清楚缺什么、为什么缺、哪天登记的。补数据这件事，留给以后有独立样本需求的时候再做，而不是今天顺手做掉。

**账本先于修复。** 说不清楚缺什么，就不要开始补。

## 五、告警的价值不在修复

这里有一个容易被忽略的事实：昨天之前，系统一直“没有报错”，不是因为一切正常，而是因为没人检查。

告警上线第一天的产出，不是修好了什么，而是把“我们不知道”变成了“我们知道缺什么”。

这件事听起来很朴素，但它改变了整个系统的自我描述方式。以前被问“最近数据完整吗”，只能回答“应该没问题”；现在可以回答：最近二十个交易日里，有九天存在缺口，分别缺哪几项，其中五天是整晚未运行，四天是部分任务漏跑。

**一个系统的健康度，不取决于它有多少天没报错，而取决于它能不能说清楚：哪几天缺、缺的是什么、为什么缺、打不打算补。**

## 六、抑制不是忘记

登记之后，巡检不再推送这九天的信息。乍看像是“把问题藏起来了”。

区别在于载体：台账里的每一条都能查到日期、缺失项、原因和登记时间；而每天的重复告警只是同一句话，三天之后就没人看了。告警系统最大的敌人从来不是漏报，是“狼来了”。

所以白名单只对“推送”生效，不对“检查”生效——缺口仍然每天被检查一遍，只是不再每天喊人。检查是为了防止情况继续恶化，不喊是为了让真正的新问题还能被看见。

这两件事分开之后，告警才可能长期有效。

## 七、这一轮留下的三条

**视野要覆盖“可能缺的那几天”，而不是“最新的那一天”。** 状态检查如果只看终点，就会把过程里的坑全部抹平。

**账本先于修复。** 先登记、再判断能不能补；直接开补，很容易把“缺失”变成“错误”。

**告警上线第一天，先验证它报的账对不对，再谈它有没有用。** 第一次就报出九条历史缺口的告警，比一条都不报的告警更值得信任。

## 写在最后

自动化做到后面，大部分工作不是让系统多做事，而是让系统把“没做的事”记下来。

今天没有让任何一条链路跑得更快，只是让系统第一次能准确回答：这个月，我们缺过哪几天。

本文只记录工程过程，不构成任何投资建议。
